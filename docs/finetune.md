# Kev のファインチューニング（手順メモ）

Kev を自分たちの正解付きデータで追加学習させる手順です。
このエディタ（CPU で推論するだけ）では学習できないので、**GPU のあるマシンか、クラウド（Modal など）で行います**。

出典: [jaredpalmer/kev の README](https://github.com/jaredpalmer/kev#fine-tune-on-your-own-data)「Fine-Tune on Your Own Data」（2026-10-08 時点の main ブランチ）。
コマンドやオプションは、取り込む Kev のバージョン（`kev/Dockerfile` の `KEV_COMMIT`）で変わることがあるので、実行する前に本家を確認してください。

## どんなときに検討するか

まずは学習なしでできる対策を試します。選択肢の説明を書き直して、境界をはっきりさせるのが基本です。
それでも次のような状態なら、学習を検討します。

- 自社の振り分け先やエスカレーションのルールなど、公開データにはない判断をさせたい
- 日本語の入力で精度が出ない（Kev は主に英語のデータで学習されています）
- 確率を閾値に使いたいが、確率が自社のデータで校正されていない（学習すると、温度も自社のデータに合わせて校正されます）

### 例: 順序チェックで答えが変わったケース

サンプルの「VPN につながらず、社内システムにログインできません」で順序チェックを 10 回実行すると、答えが「ネットワーク」と「業務アプリ」の 2 つに分かれました（確率の振れ幅は最大 20.3pt）。

- 2 つのうち、**先に並んでいる選択肢が毎回勝っていました**（試した並び順は 8 通りで、例外はありませんでした）
- 判断材料の「VPN」がネットワークの説明と、「社内システム」が業務アプリの説明と、それぞれ言葉がそのまま一致します。そのため、もともと僅差でした（通常の判定ではネットワーク 56%・業務アプリ 30%）
- 8 通りの確率を平均すると、ネットワーク 0.51・業務アプリ 0.37 です

対策は、まず選択肢の説明で 2 つの境目をはっきりさせることです。学習する場合は、学習データの選択肢の並び順をランダムに入れ替えておくと、並び順の偏りを減らせる可能性があります（これは本家に書かれていることではなく、こちらの仮説です）。

## 手順

### 1. 正解付きデータを用意する

JSONL（1 行に 1 件の JSON）で用意します。中身は API リクエストと同じ形で、各質問に正解の `label` を足します。

```jsonl
{"state": "朝から VPN につながらず、社内システムにログインできません。", "questions": {"team": {"type": "choice", "instructions": "どの担当に振り分けるか？", "criteria": {"アカウント": "パスワード・権限・ログイン ID", "ネットワーク": "VPN・Wi-Fi・社内 LAN", "ハードウェア": "PC 本体・周辺機器の故障", "業務アプリ": "社内システムの不具合・操作方法"}, "label": "ネットワーク"}, "urgent": {"type": "noul", "instructions": "本日中の対応が必要か？", "label": true}, "impact": {"type": "score", "instructions": "業務への影響度", "criteria": ["影響なし", "一部の作業に支障", "業務が止まる"], "label": 2}}}
```

| 型 | `label` の書き方 |
|----|------------------|
| `choice` | 選択肢の名前 |
| `noul` | `true` / `false` |
| `score` | 0 から数えた段階の番号 |

- データのうち 10〜20% は、評価用（`heldout.jsonl`）として学習に使わずに残しておきます
- 件数の目安: 本家の例では、400 件だと精度の上がり方が誤差の範囲に収まってしまいました。1,000 件以上あると安心です
- 実データの問い合わせ履歴が足りないときは、別の LLM に作らせることもできます

### 2. 学習する（GPU が必要）

Kev-0.8B の場合です。GPU のメモリは 4GB あれば足ります。

```bash
uv run python -m kev.train --data train.jsonl \
  --base Qwen/Qwen3.5-0.8B-Base --init_from jaredpalmer/kev-0.8b \
  --epochs 2 --lr 2e-5 --batch 1 --accum 8 --dtype bf16 --checkpointing 1 \
  --device cuda --out runs/mine
```

- **`--init_from` は必ず付けます**。公開済みの Kev から始めて、手元のデータの分を上乗せする形になります。付けずにベースモデルから学習すると、Kev がもともと持っている判断力が失われます（本家には、精度が 0.84 から 0.33 に落ちた例が載っています）
- `--base` は、`--init_from` に指定したモデルの元になったベースモデルに合わせます（0.8B なら `Qwen/Qwen3.5-0.8B-Base`）
- 学習率は小さめにします（`2e-5` から始めるのがよいとされています）

### 3. 評価する

```bash
uv run python -m kev.benchmark --run runs/mine --data heldout.jsonl --out runs/mine-eval
```

学習前のモデルと比べて、評価用データでの精度が上がったかを確かめます。

### 4. 学習したモデルを動かす

```bash
uv run --extra serve python -m kev.serve --run runs/mine --port 8009
```

このエディタから使うときは、学習済みモデル（`runs/mine`）を読み込むように kev コンテナを変える必要があります（まだ対応していません）。

## 別の方法: コーディングエージェントに任せる

```bash
npx skills add jaredpalmer/kev@kev-finetune
```

このスキルを入れて、エージェントに「Kev をうちの問い合わせデータでファインチューニングして」と頼むと、次の作業をすべてやってくれます。

- 質問の洗い出し
- 正解付きデータの作成（足りない分は LLM で生成）
- Modal での学習と、温度の校正
- 学習前のモデルとの比較
- API の公開と、後片付け

手元に GPU は要りません。費用は、Kev-4B で 1 回 1 ドルくらいです（本家の記載）。

## 注意

- 学習したモデルが強くなるのは、**学習データと似た問い合わせに対してだけ**です。ほかの種類の問い合わせまで精度が上がるわけではありません
- 社内の問い合わせ履歴を学習データに使うときは、外部のサービス（Modal、LLM での生成など）に送ってよい情報かを先に確認してください
